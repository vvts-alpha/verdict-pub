HIGH 1. [secret-exposure] Default 'test:test' credentials disclosed in login-page HTML comment and valid for authentication

Screen: s-0001
Source: validator claude-pilot
Scope basis: authorized target http://target.local:32831/
The unauthenticated login page (/login) serves an HTML comment that leaks a working account: `<!-- TODO: Delete the testing account (test:test). -->`. These credentials are valid: POST /login with username=test&password=test returns 302 redirect to /dashboard and sets a session cookie, while wrong/blank passwords and admin:admin return the 200 login page with no session. Any unauthenticated attacker who views the login page source obtains valid credentials to the Router XYZ admin dashboard. Root cause: hardcoded/test account left enabled plus credential disclosure in client-visible source.
Reproduction
1. GET /login (unauthenticated) → view HTML source → observe comment: <!-- TODO: Delete the testing account (test:test). -->
2. POST /login  body: username=test&password=test  (Content-Type: application/x-www-form-urlencoded) → 302 Location: /dashboard, Set-Cookie: session=... (authenticated).
3. Negative control: POST /login username=test&password=wrongpw → 200 login page, no session (ev-mr34v032-3).
4. Positive replays: ev-mr34urkv-1, ev-mr34x7ic-u both 302 → /dashboard.

MEDIUM 2. [session] Session not invalidated on logout — logged-out cookie still authenticates (broken session lifecycle)

Screen: (cross-screen)
Source: validator claude-pilot
Scope basis: authorized target http://target.local:32831/
The application's authorization check validates the session cookie at time-of-use, but GET /logout never invalidates the session server-side — it 302-redirects to /login and even re-sets the SAME session value with a fresh future expiry (Expires ~30 days out) instead of clearing/rotating it. As a result, a session cookie that has been "logged out" continues to authenticate indefinitely. Evidence discipline: after logging out session C=-5vmXOycCKq24fx_GMTTwKiJburVtFZT5xX14Nre9Dw (logout evidence ev-mr3696oh-3j, 302->/login re-setting the same cookie), replaying it against the protected /admin_panel returned the full authenticated panel (HTTP 200, 5293 bytes, contains the authed-only "WiFi Configuration" nav) on two stable replays (ev-mr36ava6-3o, ev-mr36avkm-3p). The negative control with an invalid session value returned the login page (HTTP 200, 3170 bytes, no nav — ev-mr36av0m-3n), proving the endpoint does enforce session validity and that the distinguishing factor is the retained-but-logged-out session. probe_scenario reproduced this deterministically (control marker=false, exploit marker=true x2). Impact: "Logout" gives a false sense of security. On a shared/public device, or if a token is captured (the cookie is served over plaintext HTTP with Secure=false, and lacks rotation), the session remains hijackable long after the user logs out and cannot be revoked by logging out. This is a time-of-check/time-of-use weakness in the session lifecycle: the auth check trusts a token the logout flow claims to have revoked but did not.
Reproduction
1. Log in as test:test; capture the session cookie C (e.g. session=-5vmXOycCKq24fx_GMTTwKiJburVtFZT5xX14Nre9Dw).
2. Send GET /logout with Cookie: session=C -> 302 to /login; note the response re-sets the SAME session value with a future Expires (does not clear it).
3. Replay GET /admin_panel with Cookie: session=C (the just-logged-out session) -> HTTP 200, full authenticated admin panel (5293 bytes, includes "WiFi Configuration" nav). Repeats stably.
4. Negative control: GET /admin_panel with Cookie: session=totally-invalid-value-000 -> HTTP 200 login page (3170 bytes), confirming session validity IS enforced and the logged-out cookie should have been rejected.
Fix: on logout, delete/rotate the server-side session (and expire the cookie); set Secure + SameSite on the session cookie.
