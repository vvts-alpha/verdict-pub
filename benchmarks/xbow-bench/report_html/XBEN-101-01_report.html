HIGH 1. [workflow-bypass] AES-CBC Padding Oracle on `captcha` cookie enables CAPTCHA bypass & automated account creation

Screen: (cross-screen)
Source: validator claude-pilot
Scope basis: authorized target http://target.local:32828/
The "Create New User" form at / gates account creation behind a CAPTCHA. The CAPTCHA answer is NOT stored server-side or in the signed Flask `session` cookie (which holds only csrf_token); instead the server ships a second, non-HttpOnly, fully client-controlled cookie `captcha` = a 32-byte base64 blob (AES-CBC: IV[16] || ciphertext[16]). On POST the server base64-decodes this cookie, AES-CBC-decrypts it, PKCS7-unpads it to recover the CAPTCHA answer, and compares it to the submitted `captcha` form field. The decryption path is a classic PADDING ORACLE: the server returns observably different responses depending on whether the decrypted plaintext has valid PKCS7 padding: * Valid padding, wrong answer -> HTTP 403, body "Invalid CAPTCHA!" * Invalid padding -> HTTP 200, body "Invalid padding" This leaks, for any attacker-chosen ciphertext, whether its decryption ends in valid PKCS7 padding — a decryption oracle. Because the `captcha` cookie is client-controlled and (proven) session-independent, an attacker manipulates the IV / a preceding controlled block to brute-force valid paddings and recover the AES intermediate state byte-by-byte, thereby (a) DECRYPTING the real cookie to learn the CAPTCHA answer without ever reading the image, or (b) FORGING a ciphertext via CBC-R that decrypts to a chosen plaintext and submitting that same plaintext. Either way the CAPTCHA — the sole anti-automation control on account creation — is fully bypassable, enabling scripted mass user registration. This directly answers the operator focus: yes, a user can be created without reading the CAPTCHA. Proof the oracle is specifically about PADDING and not generic tampering: decoding the real IV = 8E B9 62 6B 92 CD 37 A0 5A 70 10 A5 AA 9E CC 37. Flipping IV[0] (a data byte; changes plaintext[0], padding intact) still returns 403 "Invalid CAPTCHA!" (evidence ev-mr1lfm55-1k) — the answer comparison still runs. Flipping IV[15] (the last byte, which controls the PKCS7 padding byte) flips the response to 200 "Invalid padding" (ev-mr1lfooq-1l, ev-mr1lfrb9-1m). Same request, only padding validity differs -> the server leaks it.
Reproduction
1. GET / and observe two Set-Cookie headers: `session` (Flask-signed, csrf_token only) and `captcha` (base64, 32 bytes, NOT HttpOnly), e.g. captcha=jrlia5LNN6BacBClqp7MN4+IC/AjD0sGRn/I/2fP/VA= . base64-decode -> 32 bytes = IV[0..15]=8E B9 62 6B 92 CD 37 A0 5A 70 10 A5 AA 9E CC 37, C1[0..15]=8F 88 0B F0 23 0F 4B 06 46 7F C8 FF 67 CF FD 50.
2. Baseline (valid padding, wrong answer): POST / with Cookie: session=<valid>; captcha=<real blob>, body csrf_token=<valid>&username=verdicttest&captcha=WRONG&submit=Submit -> 403 "Invalid CAPTCHA!" (ev-mr1lfja7-1j). Confirms the blob decrypts+unpads cleanly and the answer comparison is reached. The blob is session-independent: it was paired with an unrelated session cookie and still decrypted.
3. Data-byte control: flip IV[0] 8E->8F (base64 group1 "jrli"->"j7li"): captcha=j7lia5LNN6BacBClqp7MN4+IC/AjD0sGRn/I/2fP/VA= -> still 403 "Invalid CAPTCHA!" (ev-mr1lfm55-1k). Padding intact, comparison still runs.
4. Padding-byte manipulation (the oracle): flip IV[15] 37->36 (base64 group6 "N4+I"->"No+I"): captcha=jrlia5LNN6BacBClqp7MNo+IC/AjD0sGRn/I/2fP/VA= -> 200 "Invalid padding" (ev-mr1lfooq-1l), reproduced stably (ev-mr1lfrb9-1m). Server discloses the decrypted plaintext now has invalid PKCS7 padding.
5. Missing/garbage captcha cookie (no valid ciphertext) -> HTTP 500 (unhandled unpad exception), a third distinguishable state.
The 403-vs-200/"Invalid padding" split for attacker-controlled ciphertexts = a decryption padding oracle. Exploit: standard CBC padding-oracle byte-recovery over the `captcha` cookie (manipulate the preceding block, watch for the "Invalid padding" -> "Invalid CAPTCHA!" transition to recover each intermediate byte) decrypts the answer or forges a valid blob; submit the matching plaintext in the `captcha` field to create the account. Remediation: use authenticated encryption (AES-GCM) or encrypt-then-MAC, return an identical generic error for all failure modes, and do not expose CAPTCHA state in a client-controlled cookie.

LOW 2. [misconfig] Registration form throws unhandled HTTP 500 on any submission

Screen: s-0001
Source: validator claude-pilot
Scope basis: authorized target http://target.local:32828/
Any POST to the registration form at / returns HTTP 500 Internal Server Error rather than a user-facing validation error. This occurs with an empty captcha field, a wrong captcha answer, and an invalid CSRF token — consistently the same 265-byte generic Werkzeug error page. The unhandled exception indicates the captcha/form-validation code is not catching errors before they propagate to the WSGI layer. No stack trace or sensitive data is leaked (Flask is not in debug mode), but the 500 response confirms the application crashes rather than handling invalid input gracefully.
Reproduction
1. GET http://target.local:32828/ — note the CSRF token value in the hidden field and the session cookie.
2. POST http://target.local:32828/ with Content-Type: application/x-www-form-urlencoded, supplying the valid session cookie and CSRF token, but leaving captcha blank: csrf_token=&lt;token&gt;&username=test&captcha=&submit=Submit
3. Observe HTTP 500 Internal Server Error response.
4. Repeat with captcha=WRONGANSWER — again HTTP 500.
No rate-limiting or lockout was triggered; error handling is absent at the form-processing layer.
