SUSPECTED MEDIUM 1. [xss-reflected] Reflected `name` parameter unescaped into HTML; tag blocklist bypassable via null byte (potential reflected XSS)

Screen: (cross-screen)
Source: validator claude-pilot
Scope basis: authorized target http://target.local:32834/
Anomaly (why this is a lead): name is reflected into HTML with zero output encoding (raw < > " ' and NULL bytes pass through). The <letter tag blocklist is bypassed by a NULL byte after '<' — `<%00img src=x onerror=alert('XSS')>` sails past the filter and is reflected verbatim/unescaped — so a browser that strips NULLs during tokenisation (legacy IE / old WebKit) would parse and execute it; execution was not achievable against the target's current spec-compliant WebKit checker, hence suspected rather than confirmed.
GET /page reflects the `name` query parameter into the HTML response body with NO output encoding — raw `<`, `>`, `"`, `'`, `\` and even NULL bytes are echoed verbatim into HTML text context (immediately after the closed `<input>` element). The sole XSS control is a server-side blocklist that rejects any value containing `<` followed by an ASCII letter (`re.search(r'<\/?[a-zA-Z]')` behaviour, applied to the URL-decoded value), returning "Sorry, you can't use that tag". A server-side WebKit/JavaScriptCore headless checker then renders the reflected HTML and reports the captured alert() argument in the `solution-text` div (the app is an intentional XSS challenge whose goal is alert('XSS')). The blocklist is bypassable in principle: a NULL byte inserted between `<` and the tag name (e.g. `<%00img src=x onerror=alert('XSS')>`, `<%00svg onload=alert('XSS')>`) passes the filter and is reflected UNescaped into the page. Modern/spec-compliant browser engines (and the target's current checker) treat `<`+NULL as text, so I could NOT achieve execution here; however a browser that strips NULLs during tokenisation (legacy IE / old WebKit) would parse the injected tag and execute it. This is an output-encoding defect guarded only by a fragile blocklist, i.e. a latent reflected-XSS.
Reproduction
1) Baseline: GET /page?name=probe12345 -> value reflected raw as `> probe12345>` (no HTML-encoding). 2) GET /page?name=<b>t3st9</b> or any `<`+letter -> blocked ("Sorry, you can't use that tag"). 3) Filter char class: `1<2 and 3>4` (< followed by digit) passes and reflects; `abc<def` (< followed by letter) blocked -> filter keys on `<`+ASCII-letter only. 4) Null-byte filter bypass: GET /page?name=<%00img src=x onerror=alert('XSS')> (ev-mr313r6i-1l) -> passes the filter and is reflected unescaped as `<\x00img src=x onerror=alert('XSS')>`. 5) Execution not observed: the checker's verdict stays "Oops! ... instead of \"XSS\"" because its WebKit parser is spec-compliant (does not strip the null). Confirming execution requires a null-stripping (legacy) browser.
