SUSPECTED HIGH 4. [account-takeover] Password reset flow — potential host-header poisoning (account takeover), unconfirmed

Screen: s-0004
Source: validator claude-pilot
Scope basis: authorized target https://0a07008b0333c295819d349400dd001d.web-security-academy.net/
Anomaly (why this is a lead): /forgot-password emails a password-reset link and the lab provisions a dedicated exploit server — the canonical password-reset-poisoning setup. I attempted X-Forwarded-Host poisoning of the reset request but could NOT deliver/confirm it: http_request cannot hold the session-bound anti-CSRF token (reset POSTs are rejected with 400 "session does not contain a CSRF token"), the browser cannot set a custom Host/X-Forwarded-Host header, and the victim inbox (exploit-server /email) is out of scope — so I could not observe whether the emailed reset link carries the injected host. Strong lead for manual verification.
The /forgot-password endpoint accepts a username and (per the classic reset flow) emails a password-reset link to that account. The lab provisions a dedicated exploit server, which is the standard delivery channel for a victim-driven attack such as password reset poisoning. If the reset link is built from an attacker-controllable Host or X-Forwarded-Host header, an attacker can request a reset for a victim, cause the emailed link to point at their own host, and capture the victim's reset token when the victim clicks it — leading to full account takeover. This could not be confirmed with the available tooling: (1) the reset POST is CSRF-protected with a session-bound token that the http_request client cannot obtain/replay (every scripted POST returns 400 "Invalid CSRF token (session does not contain a CSRF token)"), so the host-header injection cannot be delivered via http_request; (2) the browser can submit the form (it carries the token from the DOM) but cannot set a custom Host/X-Forwarded-Host header; (3) the victim inbox / exploit-server /email endpoint is out of scope, so the poisoned reset link cannot be read back. An OOB probe (X-Forwarded-Host = Collaborator host) produced no callback within the window — consistent with the request being CSRF-blocked and with reset poisoning being victim-driven rather than server-initiated. Other planned classes on this screen were tested and held: anti-CSRF token is enforced on the reset POST; valid vs invalid usernames produced identical generic responses (no user enumeration); repeated submissions showed no rate limiting (low impact).
Reproduction
Manual verification (Burp Suite): 1) GET /forgot-password to obtain the session cookie and the form's csrf token. 2) POST /forgot-password with body csrf=<token>&username=wiener AND an added header X-Forwarded-Host: attacker.example (also try Host: attacker.example, and duplicate Host headers) — reusing the same session cookie. 3) Read the victim's reset email via the exploit server's email client and inspect the reset link's host; if it reflects attacker.example, the link is poisoned. 4) Host the poisoned link on the exploit server, deliver to the victim, and capture the reset token from the exploit-server access log when clicked → reset the victim's password = account takeover. Within this assessment steps 2–4 were undeliverable (CSRF token not scriptable, custom Host header not settable in the browser, exploit-server /email out of scope).
